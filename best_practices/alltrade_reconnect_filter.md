# Защита от старых сделок и дисконнекта (OnAllTrade Desync Protection)

## Проблема (Backlog / Reconnect Surge)
При обрыве интернет-соединения или перезапуске терминала QUIK не получает котировки в реальном времени. При восстановлении связи QUIK пакетно выгружает все накопленные на сервере обезличенные сделки (OnAllTrade) за период оффлайна (от нескольких секунд до нескольких часов).

Если торговый робот анализирует рынок через OnAllTrade без проверки времени сделки, он воспримет исторический пробой (случившийся несколько минут назад по старой цене) как актуальный сигнал и отправит рыночную заявку в текущий стакан, что приводит к гарантированному убытку.

---

## Статистика задержек на практике (Замеры на SPBFUT, 01.09.2026)
На основе анализа 5418 тиков (alltrade_log.txt):

| Показатель | Значение |
|---|---|
| Абсолютный минимум | -251 мс |
| Абсолютный максимум | +5813 мс |
| Средняя задержка | +674 мс |

### Распределение
* **Штатный режим (онлайн):** задержка доставки тика составляет от **0 до 1.0 сек** (~90% всех тиков).
* **Микровсплески / пачечная доставка:** задержка может кратковременно подскакивать до **3-5.8 сек** (< 1% тиков).
* **Реальный дисконнект / догрузка:** задержка составляет **> 10-30+ сек**.

### Про отрицательные значения (-40...-251 мс)
Отрицательная дельта (PC < Биржа) означает, что **часы компьютера отстают от часов биржевого сервера** на 40-250 мс. Это НЕ ошибка кода -- это нормальный рассинхрон системных часов, неизбежный даже при NTP-синхронизации. Для задачи определения свежести тиков (секундная точность) это не влияет на работу фильтра, т.к. допуск -2 сек заложен в функцию.

## Рекомендуемый стандарт защиты

1. **Порог отсечения (max_trade_lag_sec):** **7-10 секунд** (оптимально: 8 сек).
   * Меньше 3 сек ставить нельзя -- будут ложные блокировки при нормальных рыночных микровсплесках.
   * Больше 15 сек ставить опасно -- цена на фьючерсах успевает уйти слишком далеко.

2. **Время стабилизации потока (min_stable_sec):** **3-5 секунд**.
   * Привязан ко ВРЕМЕНИ, а не к количеству тиков.
   * На ликвидном фьючерсе 5 тиков прилетают за доли секунды -- счетчик тиков бесполезен как мера стабилизации.
   * 5 секунд -- достаточный интервал, чтобы убедиться, что поток устойчиво свежий, а не случайный одиночный тик в хвосте пакета.

3. **Разделение логики:**
   * **Сбор данных / расчет свечей и фракталов:** выполняется ВСЕГДА (робот обязан восстановить исторические уровни).
   * **Торговые сигналы / отправка транзакций:** блокируются до полной стабилизации онлайн-потока.

## Эталонная реализация в коде

`lua
-- ==========================================
-- ПАРАМЕТРЫ ЗАЩИТЫ ОТ СТАРЫХ СДЕЛОК
-- ==========================================
max_trade_lag_sec = 8       -- Порог возраста сделки в секундах
min_stable_sec    = 5       -- Сколько секунд поток должен быть свежим для разрешения торговли
online_start      = nil     -- Момент начала стабильного онлайн-потока (os.time)

function CheckTradeFreshness(alltrade)
    if not alltrade or not alltrade.datetime then return false end

    local tr_sec  = os.time(alltrade.datetime)
    local pc_sec  = os.time()
    local lag_sec = pc_sec - tr_sec

    -- Тик считается свежим, если лаг не превышает порог (с допуском -2 сек на рассинхрон часов)
    local is_fresh = (lag_sec <= max_trade_lag_sec) and (lag_sec >= -2)

    if is_fresh then
        if not online_start then
            online_start = pc_sec  -- Фиксируем момент начала свежего потока
        end
    else
        online_start = nil  -- Сброс: обнаружен старый тик
    end

    -- Торговля разрешена только если поток уверенно свежий на протяжении min_stable_sec секунд
    return is_fresh and online_start ~= nil and (pc_sec - online_start) >= min_stable_sec
end
`

### Использование в роботе

`lua
dofile(Y:/Knowledge/best_practices/alltrade_reconnect_filter.lua)

function OnAllTrade(alltrade)
    -- Сбор данных (ВСЕГДА, даже при реконнекте)
    ProcessCandle(alltrade)

    -- Торговля (только при стабильном онлайне)
    if CheckTradeFreshness(alltrade) then
        CheckSignal(alltrade)
    end
end
`
